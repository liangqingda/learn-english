# Response conventions

- Every user-facing response must begin with a concise Markdown H4 title (`#### ...`) that dynamically summarizes the current response's content or task type. Do not place any visible text before the title. Titles such as `#### 复习`, `#### 英语学习`, `#### 习题讲解`, `#### 错题记录`, or `#### 规则维护` are examples only; do not treat them as fixed required wording.
- When any skill is used, including system, personal, or non-repository skills, the absolute final line of the response must be `*Generated by <skill-name> skill*`, replacing `<skill-name>` with the skill's actual name. Place one Markdown divider (`---`) immediately before the final attribution block.
- Do not add any text, punctuation, list marker, or other content after the skill attribution line.
- Put every standalone italic metadata or provenance line, including `*Picked from ...*`, only in the final attribution block. Do not place such lines in the title, teaching body, exercise body, or menu area.
- When a Git commit was created during the current turn, include exactly one visible commit notice: `*Committed -- <message>*`, replacing `<message>` with the exact commit message and adding no surrounding brackets. Do not also mention the same commit in the body text. Omit this line when no commit was created.
- Use exactly one Markdown divider immediately before the final attribution block. Inside that block, order the applicable standalone italic lines as provenance (`Picked from`) first, commit notice second, and skill attribution last, with no divider or blank line between them. If a skill attribution exists, it must remain the absolute final line; otherwise the commit notice is the final line when present.
- If any intended step did not actually execute, say so plainly in the body text before the final attribution block. Do not imply success for a skipped, failed, or blocked step.

# English learning menus

These rules apply to every user-facing response in this repository whenever the user's message contains any English — any word, phrase, letter, abbreviation, or expression, regardless of length, intent, or message type. A message that, after trimming whitespace, is exactly the single English word "review" or "hi" (case-insensitive), or exactly one relative path to a review note (such as `learning-record-notes/errors-before-begin-gerund-or-clause.md`, optionally wrapped in backticks or quotes), triggers the review flow (`practice-learning-records`) instead of English teaching; a note path starts that flow directly on the note's knowledge point. All other English input, even a single word like "hello", hard-triggers the English learning flow; ordinary English and unrelated messages are never exempt. The only other exception is a conversation that is itself explicitly discussing or modifying this rule file (meta-level rule dialogue), which is answered before any teaching.

**Engineering-context exemption (checked before any English trigger).** When the message is clearly a software, repository, or tooling request, it is handled as that task and no English lesson is produced. Any one of these signals is enough: a fenced code block or inline code span; a file path, file name with an extension, or a shell/Git command; programming identifiers such as `repo`, `skill`, `commit`, `merge`, `PR`, `API`, `CLI`, `JSON`, `test`, `build`, `deploy`, `refactor`; or an explicit `#dev` prefix. Typical phrasings such as “review 下 repo 用到的 skill”“这个 commit 有问题吗”“跑一下 test” therefore stay engineering tasks. A message that is nothing but one review-note relative path is the one exception to this exemption: it is the review trigger defined above, not a file operation. Strip a leading `#dev` before processing. The `learn:` prefix overrides this exemption and still forces teaching. When a message mixes a genuine engineering question with a short English quotation that the user asks about, answer the engineering task first and teach only the quoted part.

- A user message prefixed with `learn:` forces the English skill to trigger even when the message contains no English, and makes the learning intent explicit. Strip the `learn:` prefix before processing the rest of the message as the English learning input (knowledge-point summary, teaching, exercise, or review as the content warrants). The prefix is a hard trigger that overrides the single meta-dialogue exception above; any message already containing English triggers without it.

- End the teaching content with a numbered menu containing concrete next-step learning options. Exception: any response that presents an unanswered exercise, review question, or complete exam paper must use that exercise as the sole action surface: do not show a menu, and wait for the user's answer or explicit exit.
- Introduce the menu with `➡️ 接下来可以回复数字：`, and always place one Markdown divider (`---`) immediately before that menu intro line in every English learning response that shows a menu.
- Show the fixed Markdown H5 headings `##### Popular Menus` and `##### Other Menus` only when both groups contain at least one visible menu item. If either group would be empty, omit both group headings and list all visible menu items directly under `➡️ 接下来可以回复数字：`; do not display an empty group or write `无`. By default, put every visible option in the non-popular group. If the user has explicitly told you that specific stable menu intents belong in `Popular Menus`, place only those visible matching options in the popular group. Number top-level options consecutively from `1` across both groups; do not restart in `Other Menus`. When an option contains `children`, render them below the parent as `1-1`, `1-2`, and deeper descendants as `1-1-1`. Keep these paths stable while that menu remains current, and interpret a later pure numeric path against the latest visible menu tree.
- Review menus opened by `practice-learning-records` are the exception to the previous grouping rule: every review-related response that shows a menu must display `##### Popular Menus` and include at least one visible review-continuation or navigation option. Put returned options with kind `review-path`, `continue-review`, `familiar-review`, `mastered-review`, `mastered-exam-paper`, `paper-history`, `historical-unanswered-paper`, `continue-paper-attempt`, or `retry-random-paper` in `Popular Menus`. Also put `explain-current-exercise` there only after an erroneous answer and before that error has been explained; when visible, render it first. Keep every other returned kind under `Other Menus`, with at least 3 dynamic options whenever the script returns them. Preserve every script-provided label exactly.
- Menus are generated by the script, not hand-assembled by the model. Before showing any normal English learning menu, run the matching command: `python3 learn-from-english/scripts/learning_records.py menu --context learn --focus "<本轮核心表达>"` for teaching (add `--grammar-explained` once the grammar point was substantially explained), and `menu --context initial` / `menu --context review-complete --focus "<知识点>"` for review. Shared paper-history options are already merged into that output; do not run `paper-menu` separately. Insert every returned top-level option and its children into the group named by its `group` field without changing its `kind`, `action`, order, title, or enabled state. Skip this command while an unanswered exercise is the sole action surface or while a failed save recovery menu is active.
- Give sibling options different, semantically appropriate emoji. A nested child may reuse an emoji from a different level, but siblings under the same parent and top-level siblings must remain distinct.
- Always include a `🎭 场景对话` option tailored to the English currently being studied or reviewed. When selected, this option must output a complete multi-turn scenario dialogue script that helps the user internalize the current expression, grammar point, or error pattern; do not default to a user-participation role-play or stop after one opening line. When no English target exists yet, offer a concrete everyday scenario and provide a complete sample dialogue for that scenario. This option is mandatory in every English learning menu.
- Name the `🎭 场景对话` option from the current learning focus, not stale conversation history. Use “继续这段……” only when the user explicitly requested or is already participating in an interactive role-play dialogue and the current response is still continuing that same role-play; after switching to explanation, comparison, correction, quiz, production practice, or complete sample dialogue, relabel it as a fresh scenario for the current expression or rule.
- Always include a `📖 小故事` option tailored to the English currently being studied or reviewed, and place it immediately after the `🎭 场景对话` option. When selected, output a single-narrative story, not a dialogue: 12–20 English sentences in 3–5 paragraphs (roughly 200–400 words), the target expression used 3–4 times at turning points where its meaning or tone actually matters, one Chinese translation line after each English paragraph, and a closing three-column table (`故事里的位置` / `当时想表达什么` / `为什么不换别的表达`). Stop after that table: never append an exercise or quiz, because an unanswered exercise would take over the next turn's action surface. This option is mandatory in every English learning menu.
- Name the `📖 小故事` option from the current learning focus and never replace a real focus with the café fallback; the story's scene must follow from that focus instead of a reusable template. It is display-only: it records no score, and a complete sample story is never turned into `errors` records.
- Cover at least two activity types, such as grammar, vocabulary, comparison, pronunciation, translation, production, quiz, scenario dialogue, or story narration.
- Use specific descriptions such as `🎭 在机场问路的场景对话`; do not use vague labels such as “继续学习” or “了解更多”.
- Grammar is explained in the body, not forced to the top of the menu. If the current response has not substantially explained the grammar of the English being studied, add a grammar section to the teaching body (sentence structure, tense, clause structure, non-finite verbs, or scope of negation). Do not reorder or insert menu items to satisfy this rule — menu order always follows the script output; the teaching menu already starts its follow-up group with `🧩`.
- If grammar has already been substantially explained, run the teaching menu with `--grammar-explained` so the generic grammar-entry option is dropped, and offer a more specific grammar exercise only when useful.
- Dispatch every selected menu entry by its returned `kind`, never by guessing from its label or ID. Preserve the option ID only as its stable identity and as an argument when that `kind` requires it.
- Render options with `disabled: true` as unavailable and do not dispatch them. If the user selects one, explain that its records are temporarily claimed elsewhere and keep the current menu active.
- When the user replies with one or more top-level numbers or numeric paths from the latest menu, execute those options in order without asking them to resend the English. Then provide a new menu that follows these same rules.
- Do not interpret numbers inside ordinary English, exercise answers, or unrelated messages as menu selections.
- Tailor every follow-up and scenario option to the current record or English focus. Use the café fallback only when no record or English target exists; never replace a real record focus with that fallback.
- If saving a teaching or review result fails after evaluation, keep the exact pending payload only in the current conversation and replace the normal menu with two recovery actions: retry the same save, or discard it and continue without saving. The full retry/discard matrix lives in `practice-learning-records/SKILL.md` under “失败恢复矩阵”; follow that single source instead of re-deriving it. This recovery menu is exempt from the popular/other grouping, three-other-option, activity-variety, and mandatory-scenario rules. Do not persist ordinary review-session state. If conversation context is lost, state that the pending save cannot be resumed and return to a fresh menu.
- Number exercise questions with Arabic numerals (`1`, `2`, `3`, ...), never with `A`, `B`, `C`, and so on. Choice labels inside a question may still use `A` through `D` where required.
- The pre-menu divider is required even for pure explanations, answer evaluations, role-play turns, and menu-only responses; it visually separates the follow-up action area from the current teaching content.
- After the menu, place one divider and then the final attribution block. Put any `Picked from` provenance first, the commit notice second when present, and the skill attribution last, without blank lines between them. Do not place standalone italic metadata anywhere before the menu.

**Exercise group display format.** Every exercise group shown in the chat (review question set, follow-up practice, exam paper items) uses one fixed layout, so question blocks read alike from turn to turn:

- One `####` title covers the whole group; a single question never gets its own Markdown heading (`#`–`######`). Sizes stay flat: the group title is the only enlarged line, and every question body line keeps normal body weight.
- Each question starts with one bold head line `**<n>. <题型>**`, where `<n>` is the Arabic number and `<题型>` is one of the fixed note type names (`单项选择` / `填空` / `改错` / `改写` / `翻译` / `语境判断` / `造句` / `短写作` / `综合运用`), so the same label can be written into the note unchanged. The task wording (`选择最佳选项填空`, `改错（只改错处，句意不变）`, `中译英`, …) goes at the end of that same head line, not as a separate bold line.
- After the head line, put the stem, the options and any sub-task on their own lines as plain text — no bold, no heading, no blockquote. The stem is never bold; only the head line is.
- Choices go one per line as `A.` … `D.`; a slot the user must fill is `____`; a multipart question numbers its parts `①`, `②` at the start of the line.
- Put exactly one `---` between a question block and the next one, and no divider between the group title and the first question.
- The divider the attribution block needs is that same `---` after the last question, so the group ends: last question → `---` → attribution block. No second divider is added there.
- A complete exam paper may put bold `Part ...` / `Section ...` labels between sections; those are section breaks only — never Markdown headings — and they follow the same divider flow (`---`, then the label, then its questions).
- Never put an answer, hint, knowledge-point name, source line, or menu inside the group.

Prefer these stable emoji meanings when they fit, while keeping every item in one menu visually distinct:

- `🧩`：语法讲解或语法训练。
- `📚`：词汇、短语或搭配。
- `🔄`：近义表达、句型或语气对比。
- `🎧`：发音和听力辨析。
- `✍️`：翻译、改写或造句。
- `🎭`：带角色与背景的场景对话。
- `📖`：围绕当前知识点展开的小故事。

# Exercise and dialogue error recording

These rules apply to every skill that presents an English exercise and evaluates the user's answer, or runs an active English scenario dialogue and corrects the user's English response.

- Write an `errors` category record only when the user is answering an explicit exercise or explicitly participating in an interactive English role-play dialogue, and at least one submitted answer is judged incorrect or contains a concrete error that needs correction. Do not create an error record from ordinary English input, free conversation outside an active English-learning role-play, complete sample dialogue scripts, explanations, examples, unanswered questions, or fully correct exercise/dialogue answers.
- After explaining the error and giving the correct or improved answer, record each distinct reusable error pattern through `learn-from-english/scripts/learning_records.py`. When the same response also scores a reviewed knowledge point, include every demonstrated error in one `complete-review` coordinated write; when it completes a persisted exam paper, include them in one `paper-complete` coordinated write; for another unscored exercise or scenario dialogue, use one `batch-upsert` write. Never edit the JSON files under `learning-records/`, `mastered-learning-records/`, or `exam-papers/` directly.
- Use a stable semantic `--key` that describes the error pattern rather than the exercise, date, or conversation. Keys are lowercase ASCII letters, digits and hyphens only: translate a Chinese topic into an English phrase, because a Chinese key is rejected at write time and would otherwise put non-ASCII characters into the note file name. Use the user's incorrect answer as `--source`, and put a corrected representative sentence in `--example`.
- Error recording is independent of the active skill and independent of review scoring. When a review exercise tests an existing record, score the current record only by whether the user demonstrated the target knowledge point. If the target knowledge point was answered correctly but the response contains a different English error, treat the current record as passed while recording that separate demonstrated error in the same `complete-review` coordinated write. Scenario dialogue corrections do not by themselves trigger review scoring unless the dialogue is explicitly being used as a scored review task.
- Record only errors actually demonstrated in the submitted answer. Do not infer or invent additional weaknesses, and do not record an error merely because the overall score is below a threshold.

# Fixing reported problems

- After fixing any problem the user points out, always run a horizontal check for the same class of problem before finishing: the rest of the same section, the other sections of the same file, the other files under the same directory, and any other artifact produced from the same template or skill.
- Fix every instance found in one turn, not only the one the user named, and report the checked scope plus the result (what was found and what was fixed) in the final response.
- Verify the fix with the project's own checker or a scan script rather than by reading the diff, and state explicitly when the checker itself cannot catch the problem, so the same issue does not silently recur.

# Self-check after every change

- Any change to tracked repository content — records, papers, review notes, docs, or any skill file (`SKILL.md`, references, templates, scripts, tests) — gets a self-check pass before the commit. The pass runs **at least two rounds**, and the change is done only when a round ends with no findings and at least two rounds have run; do not wait for the user to ask for a review.
- A reply that only reads, explains, evaluates or renders a menu does not touch the repository and does not trigger the pass. Teaching and review turns do: they write records and notes, so they owe both rounds before the commit.
- Round 1 — run and read: run the checker and tests that cover what you touched, not just the edited file (`python3 take-english-study-notes/scripts/note.py check --all` for notes; `python3 -m unittest discover -s <skill>/tests` for the skill whose rule or script you changed), then re-read your own diff on four angles: (1) factual claims about the language (etymology, usage, spelling, register) — verify against a dictionary or corpus, or soften the wording instead of asserting from memory; (2) rule consistency — one rule stated once, no duplicated or drifting copy across skills, docs and templates; (3) coverage — every consumer of the changed rule or template, including other sections, other skills and notes already on disk (the same sweep as「Fixing reported problems」, applied to your own changes); (4) side effects — data fields, counters, scheduling or state the write changed silently. Fix everything found. When a skill has no test directory, report that it ran 0 tests instead of implying it passed.
- Round 2 — re-check the fixes: run the checker and tests again and re-read the **new** diff, fixes included, on the same four angles. Fixing is itself a change and can introduce a new problem: a softened claim that now contradicts another line, a rule copied into a second place, a fix that only covered the file the user named. If round 2 finds anything, fix it and run another round, until a round ends clean — two rounds is a floor, not a ceiling.
- In the final response state, for every round that ran, what was checked (checker, tests, which angles), what was found and fixed, and which part the checker cannot catch. Never call a change "self-checked" when only the checker ran.

# Note content completeness

- Every record in `learning-records/` and `mastered-learning-records/` has exactly one note file `learning-record-notes/<category>-<slug>.md`, and every note file contains the file-level `## 讲解` section. When the explanation text does not exist yet (historical backfill), keep the section with the placeholder wording from `take-english-study-notes/references/note-format.md` instead of leaving it empty or omitting it.
- Any skill that writes into a note (`append`, `append-section`, `replace`) must first confirm `## 讲解` exists and insert it with `note.py explain --update` when it is missing, before writing the new round block.
- A section in `learning-record-notes/` recording a scenario dialogue must keep the complete dialogue script, not only the bullet points: put the full turns in a `<details><summary>场景对话原文</summary>` block, with one blank line before the `**完整场景对话**：` label so it never merges into the preceding list item.
- A section recording a `📖 小故事` must keep the complete story, not only the bullet points: put the whole narrative in a `<details><summary>故事原文</summary>` block, every English paragraph followed by its Chinese translation line, and keep the closing three-column table outside the block. Bullet points alone are never a delivered story.
- A section recording exercises must keep the full question text, options and the user's answers; a section title that promises source material (dialogue, passage, example) may not ship with the material missing.
- Structural validation passing does not prove content completeness. When a checker only validates structure, say which part of the content it cannot verify.
- `learning-record-notes/categories.json` is the only category list (keys, Chinese labels, column order, `hidden`). Change a label, the order or a hidden flag there and nothing else. A brand-new category also updates `check_note.py`'s category set and the required-column table in `note-format.md`, because the validator rejects undeclared prefixes. `my-dashboard` reads this file for its English board, so never copy the list into another repo.

# Session efficiency

- A read-only menu selection (option `writes: false`: 场景对话、小故事、学习进度、错题聚类、剖析当前题、历史试卷导航) must never trigger a repository state check. No `git status`, `git log`, `git diff`, no `learning-record-notes/` scan and no note grep before answering; answer from the current conversation plus the snapshot.
- When the repository state is genuinely needed (HEAD, note file list, record→note mapping, existing round blocks and `##` sections), run one `python3 learn-from-english/scripts/learning_records.py snapshot [--record <id>] [--notes]` instead of assembling it from several shell commands. It reads a 30-minute cache that note writes no longer refresh (notes live in `take-english-study-notes`), so refresh it before a write if another session may have changed the notes.
- Before composing note content, run `python3 take-english-study-notes/scripts/note.py sections --file <note> --section "## <title>"` to see whether that section (or round block) already exists, then choose `append-section` or `replace --rewrite-section`. Never build a large heredoc first and learn afterwards that the file was renamed or the section already exists.
- Batch writes: one `batch-upsert` (or one `complete-review` for a scored round) per round's errors, never one call per question.
- Validation runs only on the write path; a read-only display never runs `check_note.py`. When a write is rejected or `invalid`, say so plainly instead of implying success.
- If the snapshot is stale or another session may have changed a note, still show read-only content optimistically and re-check only immediately before writing.

# Commit conventions

- After any repository content is added, modified, moved, or deleted, automatically create a Git commit for those changes before finishing the current turn.
- When committing, stage only the changes made for the current task. Do not include unrelated user changes.
- Use `[records]: xxx` when the commit changes only the canonical `learning-records/` data.
- Use `[papers]: xxx` when the commit changes only persisted files under `exam-papers/`.
- Use `[notes]: xxx` when the commit changes only review notes under `learning-record-notes/`.
- Use `[skill]: xxx` when the commit changes only skill files.
- Use `[readme-doc]: xxx` when the commit changes only `README.md`.
- Use `[agents-doc]: xxx` when the commit changes only `AGENTS.md`.
- Use `[refactor]: xxx` when the commit mixes more than one of the content types above.
- In every format, replace `xxx` with a concise description of the changes.
